# Handoff Tarea T04 - Módulo yt-worker (Consumidor SQS, Descarga de Audio, Fragmentación y Despacho a Whisper)

**Agente:** Gemini 3.8 Flash (T04 Implementation Agent)
**Estado:** COMPLETED
**Rama:** `feat/T01-common-module-setup`

## Resumen de cambios
- Se incorporó el módulo ejecutable `yt-worker` al proyecto multi-módulo en el `pom.xml` raíz y en `yt-worker/pom.xml`.
- Se configuraron las dependencias de Spring Boot 4, Spring Cloud AWS 4.2.0 (`spring-cloud-aws-starter-sqs` y `spring-cloud-aws-starter-s3`), Spring Data JPA y `mssql-jdbc`.
- Se creó la clase principal `YtWorkerApplication` y se aisló la configuración JPA en `JpaConfig`.
- Se implementó la abstracción de procesos CLI:
  - `CliProcessRunner` y `DefaultCliProcessRunner`: Invocan comandos del sistema operativo (`ProcessBuilder`) con lectura concurrente de streams y timeouts configurables.
- Se implementó `AudioProcessingService`:
  - `downloadAudio`: Ejecuta `yt-dlp -f bestaudio -x --audio-format mp3 --no-playlist` para descargar únicamente el flujo de audio.
  - `splitAndNormalizeAudio`: Ejecuta `ffmpeg` con parámetros `-f segment -segment_time 300 -c:a libmp3lame -ac 1 -ar 16000 -b:a 64k -reset_timestamps 1` para convertir a audio Mono de 16 kHz y 64 kbps dividido en fragmentos de 5 minutos (300 s).
- Se implementó `S3AudioUploadService`:
  - Construcción estandarizada de llaves S3: `youtube/{channelId}/{year}/{month}/{videoId}/chunk_{index}.mp3`.
  - Subida mediante `S3Template` de Spring Cloud AWS.
- Se implementó `TranscriptionApiClient`:
  - Cliente HTTP (`RestClient`) que consume el endpoint de transcripción externo `POST /api/v1/transcriptions` con cabecera `X-API-Key` y deserializa el `jobId` (UUID) según el contrato `C5-external-apis.md`.
- Se implementó `DownloadJobListener`:
  - Consumidor SQS con `@SqsListener("${yt.sqs.download-queue:youtube-download-queue}")`.
  - Orquestación completa de la descarga, segmentación, subida a S3, persistencia en `youtube.youtube_audio_chunk`, despacho a la API de Whisper (cuando `stationId != null`) y actualización de estado en `youtube.youtube_video`.
  - Limpieza garantizada de archivos temporales de audio en disco en bloque `finally`.
  - Manejo de reintentos con transición a `FAILED` al alcanzar el límite configurado (`max-attempts`).
- Pruebas automatizadas (8 pruebas pasando al 100%):
  - `AudioProcessingServiceTest` (4 tests)
  - `TranscriptionApiClientTest` (1 test)
  - `DownloadJobListenerTest` (3 tests)
- Verificación completa: `.\mvnw.cmd -B verify` ejecutado con éxito en todo el reactor (46 tests totales, 0 fallos).

## Decisiones tomadas
- Para garantizar portabilidad total en entornos de CI y desarrollo donde `yt-dlp` o `ffmpeg` no estén instalados, la ejecución CLI se desacopló mediante la interfaz `CliProcessRunner`, lo que permite probar la lógica de procesamiento y errores con mocks puros.
- El timestamp local de cada chunk (`aired_at_local`) se calcula sumando el offset en segundos a partir de `virtualStart` o la fecha de publicación ajustada a la zona horaria del canal (`America/Mexico_City` por defecto).
- Si un canal no tiene `stationId` configurado, los fragmentos de audio se descargan, normalizan y suben a S3 (quedando en estado `AUDIO_READY`), pero no se despachan a la API de Whisper para evitar errores de validación externos.
